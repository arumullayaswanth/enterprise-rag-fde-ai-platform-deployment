An FDE (Forward Deployed Engineering) project — building a production Retrieval-Augmented Generation platform on AWS.

🎯

What we're building

A RAG system that answers questions about company knowledge — people, policies, performance — with grounded, cited answers. Every answer comes from your own documents, not guesses.

⚙️

How it works

Documents become vectors stored in OpenSearch. A question is embedded, matched to the closest chunks, and an LLM writes the answer from that context.

☁️

Built on AWS

Bedrock (Titan + Nova), OpenSearch, ECS Fargate, Lambda, S3, ALB — provisioned with modular Terraform and shipped through a one-click GitHub Actions pipeline.

🧑‍💻

Full stack

A React + TypeScript frontend talks to a FastAPI backend. One ECS container serves both the API and the website.

The whole story — in plain English

No jargon. Just read top to bottom and you'll understand exactly what this project does and what happens behind the scenes.

1 · What problem are we solving?

A normal chatbot makes things up when it doesn't know an answer. We don't want that. We want a system that answers questions only from our own company documents — and tells you which document it got the answer from. That is what "RAG" means: it Retrieves the right information first, then Generates an answer from it. No guessing.

2 · First, we teach the system our documents (ingestion)

Before anyone can ask anything, the system has to read and remember our documents. Here is how that happens, step by step:

Someone uploads a file (a PDF, a Word-like doc, a spreadsheet of employees) into an S3 bucket — think of S3 as a big, safe folder in the cloud. The moment a file lands there, it automatically wakes up a small program called a Lambda (a function that runs only when needed, then goes back to sleep — so it's cheap).

The Lambda does three things. First it splits the document into small bite-sized pieces called "chunks," because a whole 50-page PDF is too big to work with at once. Then it sends each chunk to Amazon Bedrock (AWS's AI service) and asks it to turn the text into a list of numbers called a vector. That sounds strange, but a vector is just the "meaning" of the text written as numbers — two chunks about the same topic get similar numbers. Finally, it saves both the original text and its vector into OpenSearch, which is a special database built to search by meaning, not just keywords.

After this runs, our documents are "learned" and searchable. We only do this once per document.

3 · Now a user asks a question (the live part)

A user opens the website and types something like "Who does Yaswanth Reddy report to?" and hits send.

That request travels to a load balancer (the public front door that keeps traffic organized), which passes it to our application running on ECS Fargate — this is just a container in the cloud running our code, with no servers for us to manage. The front end is React (what you see and click); the back end is FastAPI in Python (the brain that does the work). Both live in the same container.

The back end takes the question and sends it to Bedrock to turn it into a vector too — the exact same "meaning as numbers" trick we used on the documents. Now the question and the documents speak the same language.

4 · Finding the right information

The back end hands that question-vector to OpenSearch and says "find me the chunks whose meaning is closest to this." OpenSearch compares and returns the top few most relevant chunks — for our example, the row in the employee directory about Yaswanth Reddy and his manager.

We also mix in a plain keyword search and blend the two results together (this is called "hybrid" search). That way we catch both the meaning matches and the exact word matches, which gives better answers.

5 · Writing the answer

Now the back end builds a little note for the AI that basically says: "Here are the relevant chunks, and here is the user's question. Answer using only these chunks." It sends that to the LLM (the large language model, also on Bedrock). The LLM reads the chunks and writes a clean, human answer — and because we told it to stick to the provided text, it stays honest and even cites the source.

The answer travels back through the same path to the browser, and the user sees: "Yaswanth Reddy reports to Marcus Vance," with a little citation showing it came from the employee directory. Done — in a couple of seconds.

6 · How it all got there (deployment)

None of this is clicked together by hand. We describe the entire cloud setup as code using Terraform — the network, the database, the containers, the permissions, everything. When we run the deploy pipeline on GitHub Actions, it logs into AWS securely (no passwords stored — it uses a trusted handshake called OIDC), builds our app into two Docker images, pushes them to ECR (a registry for images), and tells Terraform to build the whole stack. One click and the entire platform comes to life. Another click tears it all down.

7 · A note on safety and cost

Our API is protected by a secret key (stored safely in Secrets Manager, generated automatically — we never type it). The AI models on Bedrock aren't "created" by us; they already exist in AWS and we're simply given permission to call them. And the little programs like Lambda only run when there's work to do, so we're not paying for idle servers.

In one sentence

We turn documents into searchable "meaning," find the pieces that match a user's question, and let an AI write a trustworthy answer from exactly those pieces — all running on AWS, deployed with one click.

Why do we need OpenSearch?

The embedding model only turns text into numbers. Something has to keep those vectors and find the closest ones fast. That is OpenSearch. Follow the same question through it.

✕ Without OpenSearch

You would hold all 100 vectors in memory and compare the query against every one on each request — slow, and lost the moment the app restarts. And you would still need the original chunk text to send to the LLM, which a bare vector does not carry.

✓ With OpenSearch

It stores each chunk's text + vector together, runs k-NN similarity search in milliseconds, scales past millions of chunks, and hands back the actual text — so the LLM gets real context, not raw numbers.

Deployment Steps

Do these once in the AWS Console, set the GitHub variables, then run the workflow. Nothing else.

1
Create an S3 bucket for the Terraform state (enable Versioning).
2
Create the IAM OIDC role for GitHub Actions:
  • IAM → Identity providers → Add provider → OpenID Connect
  • Provider URL: https://token.actions.githubusercontent.com · Audience: sts.amazonaws.com
  • IAM → Roles → Create role → Web identity → pick that provider + your repo
  • Attach AdministratorAccess → name it github-rag-deploy → copy its ARN

Then verify the Trust policy (Role → Trust relationships → Edit trust policy). Replace ACCOUNT_ID, GITHUB_ORG, REPO — the sub line locks the role to your repo: 

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::ACCOUNT_ID:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        },
        "StringLike": {
          "token.actions.githubusercontent.com:sub": "repo:GITHUB_ORG/REPO:*"
        }
      }
    }
  ]
}
3
Set GitHub Actions variables (Settings → Secrets and variables → Actions → Variables):
AWS_REGION e.g. us-east-1
AWS_OIDC_ROLE_ARN the role ARN from step 2
TF_STATE_BUCKET the bucket name from step 1
▶
Run it: Actions → fde-rag-deployment → Run workflow → choose apply to deploy or destroy to tear down. The Web URL prints in the run summary. That's it.
