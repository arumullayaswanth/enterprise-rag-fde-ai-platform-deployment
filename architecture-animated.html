Step by step

The same journey, written out plainly.

1

Upload & chunk

Documents land in S3; a Lambda splits them into small chunks.

2

Embed

Amazon Bedrock (Titan) turns each chunk into a vector.

3

Store

Chunk text + vector are saved in the OpenSearch vector index.

4

Ask

A user asks a question; it is embedded into a query vector.

5

Search

OpenSearch returns the Top-K most similar chunks.

6

Answer

The LLM reads those chunks and writes a grounded, cited answer.

Amazon S3 is an AWS object storage service that stores data as objects inside buckets and offers multiple storage classes for different access needs.

Why do we need OpenSearch?

The embedding model only turns text into numbers. Something has to keep those vectors and find the closest ones fast. That is OpenSearch. Follow the same question through it.

✕ Without OpenSearch

You would hold all 100 vectors in memory and compare the query against every one on each request — slow, and lost the moment the app restarts. And you would still need the original chunk text to send to the LLM, which a bare vector does not carry.

✓ With OpenSearch

It stores each chunk's text + vector together, runs k-NN similarity search in milliseconds, scales past millions of chunks, and hands back the actual text — so the LLM gets real context, not raw numbers.
